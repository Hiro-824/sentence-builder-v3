## 4. 着想に基づく具体的設計

### 4.1 GUIの設計

前節の着想を具体化するため、Syntabloでは、文法的制約を反映した英文構築の仕組みを実装した。英文構築の仕組みは、以下の三つからなる。

① ドラッグ＆ドロップによるブロック同士の接続（空所挿入と非空所付加）  
② GAP-FILLER関係による、未挿入空所の解消  
③ ドロップダウンメニューによる語形の選択と、それに伴う結合条件・空所構成の変更

このうち、第一と第三は学習者が行う操作であり、第二はブロックの接続に伴って自動で行われる表示変更である。また、これらの仕組みに加えて、句や文の構造、接続の可否、および作成した表現の意味を画面上に表示する。以下では、まず具体例を用いて画面上の操作と表示を説明し、その後、それらを支える内部のデータ構造と判定方法について述べる。

学習者は、画面上の一覧から必要なブロックを選び、ワークスペースで組み合わせて句や文を構築する。ブロック同士の接続には、ブロックに設けられた空所に別のブロックを挿入する「空所挿入」と、空所への挿入を伴わず、別のブロックに付け加える「非空所付加」の二つがある。いずれも、接続される側が親ブロック、挿入・付加される側が子ブロックとなる接続である。

空所挿入の例として、動詞と目的語の組み合わせが挙げられる。例えば、*eat* のブロックには目的語を入れる空所があり、そこに *an apple* のブロックを挿入すると、*eat an apple* というまとまりができる。一方、*sleep* のブロックには目的語に対応する空所がないため、同じ方法で *an apple* を挿入することはできない。また、空所には何でも挿入できるわけではなく、それぞれの位置に適した種類のブロックだけを挿入できる。このように、語がどのような要素と組み合わさるかを、空所の有無と挿入可能なブロックの条件によって表現した。

ブロックと空所の形にも、語や句の分類を反映させた。例えば、名詞句のブロックと名詞句を要求する空所には、対応する丸みを帯びた形を用いる。これにより、学習者は形を手掛かりとして挿入先を探すことができる。ただし、人称・数や格など、すべての結合条件を形で表しているわけではない。実際にブロックを空所に重ねると、その組み合わせが挿入可能かどうかを枠の色によって表示する。条件を満たさない場合には挿入を成立させない。

非空所付加の例としては、動作の様子を表す語を動詞句に付け加える操作が挙げられる。例えば、*eat an apple* に *slowly* を付加すると、*eat an apple slowly* となる。この場合、*slowly* は *eat* に用意された空所を埋めるのではなく、すでにある表現に説明を付け加えている。ただし、非空所付加も自由に行えるわけではなく、どの種類の表現に、どちら側から結合できるかという条件を設けた。ブロックを付加先に重ねると、付加の可否を枠の色によって表示し、条件を満たす場合にのみ付加を成立させる。

こうして作成した句も、対応する空所や付加先があれば、さらに別のブロックに接続できる。接続を繰り返した結果はブロックの入れ子として表示され、どの句がどの句・文の一部となっているかを確認できる。この包含関係は、樹形図で表されるような統語的な階層構造に大まかに対応している。

また、wh疑問文や関係代名詞を用いた表現など、空所が要求する語句がその空所とは別の位置に現れる場合も扱っている。例えば、*What did you eat?* では、*what* は文頭に現れるが、*eat* の目的語に相当する。この関係は、説明のために *What did you eat \_\_?* と表すことができる。ここで「__」は、食べた対象に対応する位置である。

この文を組み立てると、*eat* の目的語に対応する空所は、小さな丸として表示される。この丸には別のブロックを挿入できない。これにより、*what* が別の位置に現れる場合に、*eat* の目的語位置にも重ねてブロックを挿入することを防いでいる。

語形については、ブロック内のドロップダウンメニューで変更する。例えば、*eat* から *ate* への変更は、文字の入力ではなく、登録された語形の選択によって行う。また、語形の変更に伴い、そのブロックが結合できる相手や、表示する空所も変化する。例えば、*eat* を受動態に用いる形へ変更すると、能動態で目的語に対応していた空所が表示されなくなる。それに合わせてブロックの横幅も縮まり、文字列だけでなくブロックの形状も変化する。このように、語形と、それに対応する結合条件・空所構成・表示を連動させた。

このほか、作成した句や文には、その構造に基づいて組み立てた日本語訳を表示する。例えば、*eat* の目的語位置に *an apple* を挿入すると「リンゴを食べる」、さらに *slowly* を付加すると「ゆっくりリンゴを食べる」と表示される。この日本語訳は、各部分の訳を、ブロック同士の文法的な関係に応じて組み合わせることで生成する。学習者は、ブロックの操作によって、表現の意味がどのように変わるかを確認できる。

### 4.2 内部設計

ここからは、以上の操作と表示を支える内部の文法表現について述べる。

まず、空所挿入は、主要部が持つ補部要求の充足に対応する。各語には、どのような要素を左右に要求するかを記述しておき、挿入される句がその要求を満たすかを判定する。例えば、他動詞の目的語位置には、名詞句であることや、代名詞であれば目的格であることなどの条件を課す。ここでいう補部要求は、実装上、主要部が要求する要素を扱う仕組みを指し、主語などについても同じ要求・充足の枠組みを用いている。

これに対して、非空所付加は修飾関係に対応する。この場合には、修飾する側に、どのような表現を修飾できるかという条件を記述する。例えば、*slowly* には、動詞を主要部とする表現を修飾できるという条件を与える。そして、付加先の句がその条件を満たす場合に結合を認める。したがって、二つの接続方法は画面上の操作の違いであると同時に、補部要求の充足と修飾という文法的な関係の違いにも対応している。

これらの条件は、素性構造として記述した。本稿でいう素性構造とは、範疇、人称・数、格、動詞の形などについて、属性とその値を組にして保持するデータ構造である。属性の値として、さらに別の素性構造を持つ場合もある。結合時には、要求される素性構造と、実際に結合する語・句の素性構造を照合し、両者が適合するかを判定する。

この照合では、両方に記述されている属性について、その値が一致することを要求する。値が素性構造である場合には、その内部についても同じ照合を行う。一方にしか記述されていない属性は、不一致とはみなさない。また、一方の値が素性構造で、他方が文字列などの値である場合には、不適合とする。適合する場合には、両者に記述された属性と値をまとめ、その後の処理に用いる。

具体例として、4.1で示した *eat* と *an apple* の接続を取り上げる。以下のJSONは、実装で用いるデータから、説明に必要な部分を抜粋したものである。`head` は語・句自身の素性構造、`right` はその右側に要求する要素のリストを表す。*eat* には次のように記述する。

```json
{
  "head": {
    "type": "verb"
  },
  "right": [
    {
      "head": {
        "type": {
          "type": "nominal",
          "isDet": true
        },
        "case": "acc"
      }
    }
  ]
}
```

このデータでは、*eat* 自身が動詞であることに加え、右側に名詞的な要素を一つ要求することを記述している。`isDet` は、ここでは名詞単独と、限定詞を伴う名詞句や代名詞などとを区別するために用いる属性である。`case` は格を表し、`acc` は目的格を表す。

これに対して、*an apple* の `head` には次の素性が含まれる。

```json
{
  "head": {
    "type": {
      "type": "nominal",
      "isDet": true
    }
  }
}
```

挿入時には、*eat* の `right` の第一要素にある `head` と、*an apple* の `head` とを照合する。両者には `type` が記述されているため、その内部を調べると、`type` の値はともに `nominal`、`isDet` の値はともに `true` であり、矛盾しない。*an apple* には格が指定されていないため、*eat* 側の `"case": "acc"` とも矛盾しない。他の素性も適合するため、*an apple* を挿入して *eat an apple* を作ることができる。

一方、*slowly* の `head` には次の素性が含まれる。

```json
{
  "head": {
    "type": "adverb"
  }
}
```

これを *eat* の目的語位置に挿入しようとすると、要求される `type` は名詞的な要素を表す素性構造であるのに対し、*slowly* の `type` は文字列 `adverb` であり、適合しない。したがって、*slowly* を目的語の空所に挿入することは認めない。また、*sleep* では、右側の補部要求を表す `right` が空のリストであるため、目的語に対応する空所自体を設けない。

非空所付加でも同じ照合方法を用いるが、照合するのは補部要求ではなく、修飾先に対する条件である。*slowly* には、次のように記述する。

```json
{
  "head": {
    "type": "adverb"
  },
  "leftModTargets": [
    {
      "head": {
        "type": "verb",
        "adv_manner_type": "skill"
      }
    },
    {
      "head": {
        "type": "verb",
        "adv_manner_type": "degree"
      }
    }
  ]
}
```

`leftModTargets` は、その語から見て左側にある修飾先に対する条件を表す。複数の条件を登録した場合には、いずれかに適合すればよい。`adv_manner_type` は、副詞との結合を制限するために動詞に与えた実装上の分類である。この例では、`skill` または `degree` に分類した動詞を修飾先として認めている。

*eat an apple* の `head` には、次の素性が含まれる。

```json
{
  "head": {
    "type": "verb",
    "adv_manner_type": "skill"
  }
}
```

これは *slowly* の `leftModTargets` の第一要素と適合する。そのため、*eat an apple* の右側に *slowly* を付加して、*eat an apple slowly* を作ることができる。一方、*an apple* 自体は `type` が名詞的な要素を表す素性構造であり、どちらの修飾先条件にも適合しないため、*slowly* を *an apple* に直接付加することは認めない。このように、空所挿入と非空所付加では、同じ語の組み合わせであっても、参照する条件が異なる。

語形の選択については、同じ語の各語形に、それぞれの素性構造と補部要求を与えている。ドロップダウンメニューで語形が変更されると、表示する文字列だけでなく、判定に用いる素性構造も切り替わる。また、選択された語形に応じて、補部に対応する空所の表示・非表示を切り替える。例えば、受動態用の形を選ぶと、能動態で目的語に対応していた空所を表示しなくなる。変更後の素性構造を用いて既存の結合を再判定し、適合しない場合には、変更を取り消すか、該当するブロックを結合先から切り離す。

未挿入空所の解消には、GAPとFILLERの対応を用いる。未充足の要求はGAPとして保持し、その要求を表す素性構造を記録する。そのGAPを含む句がより大きな構造に組み込まれた場合にも、未解決のGAPの素性構造を上位へ引き継ぐ。そして、GAP-FILLINGを行う構造では、一方の空所に挿入される句が所定のGAPを持つことを要求し、別の空所には、そのGAPに対応するFILLERを要求する。

例えば、*What did you eat \_\_?* では、*eat* の目的語要求が未充足であることをGAPとして保持する。そのGAPを *did you eat \_\_* 全体へ引き継ぎ、疑問文を構成する段階で、目的語に対応するGAPを含む節と、FILLERとなる *what* とを組み合わせる。挿入される節が持つGAPと、要求されるGAPの素性構造を照合し、適合するGAPが確認されると、それを解決済みとして扱い、上位へ引き継ぐ未解決のGAPのリストから除く。この判定結果を画面上の表示に反映し、対応する空所を挿入不能な小さな丸に変更する。GAP-FILLINGは、空所に入る要素への条件と、要素間の対応関係を通して実現している。

日本語訳は、各語に与えた訳語や翻訳用のテンプレートに基づいて生成する。テンプレートには、補部や修飾句の訳を組み込む位置や、付加する助詞などを記述する。例えば、*eat* とその目的語からなる句では、目的語の訳に「を」を付け、その後に動詞の訳を置くことで「リンゴを食べる」という訳を生成する。このように、構成要素の訳を句構造に従って組み合わせるという意味で、日本語訳の生成は合成的に行われる。また、GAP-FILLER関係を扱う際には、解消されたGAPに対応する位置にFILLERの訳を反映する処理も行う。

以上のように、Syntabloでは、語・句の素性構造、補部要求、修飾先の条件、およびGAPとFILLERの対応を記述し、それらをブロックの構造と操作の可否に反映させた。ただし、ここで判定できるのは、アプリ内に記述した語彙情報と文法的制約の範囲である。
