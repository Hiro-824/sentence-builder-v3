## 4. その着想を、どのような具体的な設計に落とし込んだのか？

### 4.1 GUIとしての実装

第3節で示した着想を、具体的にはどのようなGUIとして実装したかについては、第1節で説明した通りである。「学習者のタスクを英語の句・文の作成とすること」と「その作成をGUIの操作によって行うこと」は、ブロックの接続と語形の選択を通じて実現した。一方、「文法的に不正確な句・文の作成を不可能にすること」については、対象とする語彙・文法の範囲を限定して実装を試みた。

句・文の作成では、語のまとまりとその包含関係が見えるよう、ブロックを入れ子に組み合わせる方式を採用した。接続方法は空所への挿入と修飾対象への付加の二つとし（F1）、それぞれに、語・句の文法的性質を記述した「素性構造」に基づく接続可否の判定を設けた。文法的な要求は空所の構成に反映し（F2）、輪郭による手がかり（F3）と、操作時の接続可否の表示（F4）を通じて学習者に提示する。また、語形の選択（F5）や長距離依存に対応した空所の処理（F6）も、この文法情報と連動させた。

ただし、この実装が判定するのは、アプリ内に定義した文法的制約への適合性である。個々の表現に対する母語話者の判断の違いや、使用される文脈まで含めて、英語全体の文法性を一意に判定するものではない。また、語彙情報と文法的制約の定義には不足があり、不適切な組み合わせを許してしまう場合や、未対応の文法事項もある。

教材としては、判定の基準となる英語の範囲を定め、その範囲内で一貫した制約を設けることに意味があると考える。定義の追加・修正によって対応範囲を広げる余地もある。このため、筆者は、文法的制約をGUI上の操作に反映するという着想を、限定的ながら具体化できたと評価している。ただし、この実装上の評価と、学習への有効性の評価は区別する必要がある。これについては、第5節以降で扱う。

### 4.2 文法性判定の実装

接続可否の判定には、語・句の文法的性質を属性と値の組で表す「素性構造」を用いた。例えば、品詞、格、人称・数、動詞の形などを記述する。属性の値として、さらに別の素性構造を持つこともできる。実装では、語ごとの設定と共通の生成処理から、各語形に対応する文法情報を作成している。

各語には、その語自身の性質に加え、左右に要求する要素の条件や、修飾できる対象の条件を記述する。挿入では、空所に要求される条件と、挿入する語・句の性質を照合する。付加では、修飾語が要求する対象の条件と、付加先の語・句の性質を照合する。画面上で組み立てられたブロックの構造をこれらの情報に変換し、接続後の構造が制約を満たすかを判定する。

具体例として、第1節で示した、主語が`She`の場合に`likes`は接続できるが、現在形の`like`は接続できないという判定を取り上げる。以下は、実装で用いる属性名と値を保ち、説明に必要な部分のみを抜粋したJSON形式の例である。描画用の情報、日本語訳、および一部の文法的属性は省略している。

`she`の文法情報は、次のように表される。

```json
{
  "head": {
    "type": { "type": "nominal", "isDet": true },
    "case": "nom",
    "agr": { "type": "3sing", "per": 3, "num": "sing" }
  }
}
```

`head`は語・句自身の性質を表す。ここでは、`type`が名詞的な要素であること、`case`が主格であること、`agr`が人称・数に関する情報を示す。`3sing`は三人称単数を意味する。`isDet`は、名詞単独と、限定詞を伴う名詞句や代名詞などを区別するための実装上の属性である。

一方、`likes`は次の情報を持つ。

```json
{
  "head": {
    "type": "verb",
    "tense": "present",
    "finite": true,
    "form": "es"
  },
  "left": [
    {
      "head": {
        "type": { "type": "nominal", "isDet": true },
        "case": "nom",
        "agr": { "type": "3sing" }
      }
    }
  ]
}
```

`left`は左側に要求する要素のリストであり、この例では主語の条件を表す。`likes`自身は現在時制の定形動詞（`finite: true`）であり、三人称単数の主格の要素を要求する。`form: "es"`は、三人称単数現在形を表す実装上の名称である。目的語の要求も別に記述されるが、ここでは省略した。

現在形としての`like`は、これに対して次の条件を持つ。

```json
{
  "head": {
    "type": "verb",
    "tense": "present",
    "finite": true,
    "form": "base"
  },
  "left": [
    {
      "head": {
        "type": { "type": "nominal", "isDet": true },
        "case": "nom",
        "agr": { "type": "non-3sing" }
      }
    }
  ]
}
```

`non-3sing`は三人称単数以外を表す。このため、`she`の`agr.type`は`likes`の主語要求とは一致するが、現在形の`like`の主語要求とは一致しない。

この照合は「単一化」という処理で行う。両方の素性構造に同じ属性がある場合は、その値の一致を求める。値がさらに素性構造であれば、その内部についても同じ処理を行う。一方にしかない属性は矛盾とみなさず、両方の情報をまとめる。途中で値が矛盾すれば、単一化は失敗する。したがって、`she`と`likes`の主語要求は単一化できるが、`she`と現在形の`like`の主語要求は、`3sing`と`non-3sing`の不一致によって単一化できない。

画面上では、主語と動詞句は文の枠の別々の空所に挿入される。内部では、動詞句に残る未充足の主語要求を保持し、文の枠に挿入された主語の素性構造と照合する。したがって、この判定は隣接する二語の文字列だけを見るものではなく、組み立てられた構造の中で対応する要素同士を照合する処理である。また、`like`には非定形の原形としての文法情報もあるが、ここで用いる文の枠は定形動詞句を要求するため、そちらの解釈によって不一致を回避することはできない。

同じ照合方法は付加にも用いる。例えば、形容詞`big`には修飾対象の条件を記述し、その条件と名詞`book`の素性構造が適合する場合に付加を認める。語形を変更した場合には、判定に用いる文法情報も切り替わる。長距離依存については、未充足の要求を空所の情報として上位の構造へ引き継ぎ、対応する要素との適合性を照合する。対応が成立した空所の識別情報を描画側に返すことで、第1節で示した小さい穴への表示変更と挿入禁止を実現する。

このように、接続の可否は、定義した語彙情報と構造上の制約を照合して決定する。新たな語や構文を扱うには、それらに必要な情報と制約を追加する必要があり、判定の範囲と精度は、その定義の範囲と適切さに依存する。
